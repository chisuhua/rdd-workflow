# rddf-session-binding — Capability Spec

> **Source**: `docs/superpowers/specs/2026-07-14-rddf-session-binding-design.md`
> **Status**: Active (deployed in v2.0.2 via merge commit `f540f48`)
> **Type**: Additive extension to ADR-0017 rddf-session

## Purpose

Provide discoverable rddf-session binding + next-session recommendation across OpenCode chat sessions, exposed via three surfaces:

1. `RddfSessionCoordinator` Python API (`find_current_binding`, `find_next_recommendation`)
2. `rddf-session current` CLI subcommand
3. `guide` recommender `BINDING_LINES` output

## ADDED Requirements

### Requirement: Binding-discovery read API

The `RddfSessionCoordinator` SHALL expose two new read-only methods that work with the existing `owner_opencode_session_id` field (no schema change).

#### Scenario: Find current binding

- **WHEN** `find_current_binding(owner_opencode_session_id)` is called
- **THEN** it returns the active rddf-session owned by that OpenCode session ID
- **AND** if multiple active sessions exist for the same owner, it returns the one with the most recent `started_at`
- **AND** if no active session exists, it returns `None`
- **AND** it does NOT consider `orphaned` sessions (those are reserved for `find_next_recommendation`)
- **AND** it uses the existing `_with_file_lock` POSIX advisory lock pattern

#### Scenario: Find next recommendation

- **WHEN** `find_next_recommendation(owner_opencode_session_id=None)` is called
- **AND** at least one `orphaned` rddf-session exists
- **THEN** it returns the orphaned session with the most recent `started_at`
- **AND** if no orphaned session exists, it returns `None`
- **AND** the `owner_opencode_session_id` parameter is reserved for future filtering (currently unused)

### Requirement: `current` subcommand

The `rddf-session` skill SHALL expose a `current` subcommand.

#### Scenario: Show current binding

- **GIVEN** the OpenCode session is bound to an active rddf-session
- **WHEN** `skill_use("rddf-session current")` is invoked
- **THEN** it prints `📍 Current: <rds_id> (kind=<K>, started=<T>)` and exits 0
- **AND** it does not modify `.rddf/state/sessions.json` (read-only)

#### Scenario: Recommend next session when unbound

- **GIVEN** no active binding for the current OpenCode session
- **AND** at least one orphaned rddf-session exists
- **WHEN** `skill_use("rddf-session current")` is invoked
- **THEN** it prints:
  ```
  📍 No current binding
  💡 Recommended: <rds_id> (kind=<K>, last_heartbeat=<T>)
     → skill_use("rddf-session resume <rds_id>")
  ```
- **AND** exits 0

#### Scenario: Empty project fallback

- **GIVEN** `.rddf/state/sessions.json` does not exist OR is empty
- **WHEN** `skill_use("rddf-session current")` is invoked
- **THEN** it prints the fallback message:
  ```
  📍 No current binding
     No orphaned rddf-sessions found. Run guide-arch or guide-plan to start.
  ```
- **AND** exits 0
- **AND** does NOT print a stack trace or error message

#### Scenario: OPENCODE_SESSION_ID fallback

- **WHEN** `OPENCODE_SESSION_ID` env var is unset
- **THEN** the `current` subcommand falls back to `$(hostname -s)_$$` (matching the existing `resume` subcommand convention)

### Requirement: guide integration

The `guide` recommender SHALL surface binding status alongside its `RECOMMEND` / `REASON` lines, without modifying the existing 11-priority scan logic.

#### Scenario: Append binding lines after REASON

- **WHEN** `scan_session_binding <PROJECT_ROOT>` is invoked from a guide flow
- **AND** `.rddf/state/sessions.json` exists and is valid
- **THEN** it populates the `BINDING_LINES` global array with 1-2 formatted lines
- **AND** these lines appear AFTER the RECOMMEND/REASON output (not before, not interleaved)
- **AND** `RECOMMEND` and `REASON` globals remain unchanged

#### Scenario: Silent skip when sessions.json missing

- **WHEN** `scan_session_binding <PROJECT_ROOT>` is invoked
- **AND** `.rddf/state/sessions.json` does not exist
- **THEN** `BINDING_LINES` is an empty array
- **AND** the function exits 0
- **AND** no error message is printed

### Requirement: Mandatory binding policy

Every workflow session generated by `guide-arch` / `guide-plan` / `guide-ship` MUST be bound to a rddf-session via the `owner_opencode_session_id` field, per ADR-0017 §Decision 2 and §Implementation.

#### Scenario: Workflow session auto-binding

- **WHEN** `guide-arch` / `guide-plan` / `guide-ship` is invoked
- **THEN** the corresponding `kind=stage_*` rddf-session is created with `owner_opencode_session_id = ${OPENCODE_SESSION_ID}` (or fallback `hostname -s_$$`)

#### Scenario: Cross-session conflict detection

- **WHEN** an active rddf-session of `kind=K` exists owned by a DIFFERENT OpenCode session
- **AND** a new invocation tries to create another `kind=K` rddf-session
- **THEN** `RddfSessionCoordinator.create_session` raises `ConflictError`
- **AND** the caller MUST invoke the 4-option soft prompt per ADR-0017 §Decision 4

## Backward Compatibility

This capability is purely additive. It does NOT modify:

- `sessions_schema.json` (v1 unchanged)
- Any existing `RddfSessionCoordinator` public method signatures (only new methods added)
- `scan_state` 11-priority logic (RECOMMEND/REASON semantics unchanged)
- The 5 existing rddf-session subcommands (list/show/resume/abandon/archive-history unchanged)
- The `guide-arch` / `guide-plan` / `guide-ship` entry hooks (already bound per ADR-0017 P2)
