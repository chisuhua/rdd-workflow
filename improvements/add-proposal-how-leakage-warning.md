# add-proposal-how-leakage-warning

**优先级**: P1 | **来源**: 质量设计审查 — improvement/proposal 的 WHY/WHAT 与 design/plan HOW 边界缺少语义提示
**阶段**: v2.1 | **分类**: quality
**类型**: feature

## 架构依据
- ADR-0019 §3.1、§3.2 确立保守的反模式检查哲学：优先低误报、默认 warning、通过实际命中数据再扩展规则，不以宽泛规则削弱门控信誉。
- ADR-0025 §D2、§D4 明确 design 阶段负责把五段 improvement 内容转换为 proposal，并将审查分为 improvements 层与 openspec proposal 层。该分层仍缺少对 WHY/WHAT 内容混入 HOW 的边界提示。
- ADR-0025 §D1 保留生成后的用户确认，因此本检查应提供可解释的辅助信号，不代替用户判断，也不把提案写成实施计划。
- 当前缺口是内容层边界检查，而不是架构一致性、依赖关系或实现正确性检查。目标是尽早提示内容层次漂移，保持 proposal 的可读性和后续设计空间。

## 范围
- **In Scope**:
  - 在 improvement/proposal 内容审查流程中增加 warning-only 的 HOW 泄漏提示。
  - 使用可解释的启发式信号组合识别可能的实现级内容，包括过多代码围栏、函数或方法签名、具体文件与模块改动列表、连续的实施步骤，以及明显偏高的实现步骤密度。
  - 按内容所在段落区分风险，重点关注架构依据、范围、关键场景和验收标准中的实现细节堆积，并展示触发信号及所在段落。
  - 提供人工忽略或确认误报的路径，并保留原文，不自动重写内容。
  - 为 improvements 层和 proposal 层定义一致的提示文案与可测试的阈值配置。
- **Out Scope**:
  - 不引入 LLM 语义分类器、嵌入检索或其他需要模型判断的内容分类方案。
  - 不默认阻断创建、审批、design-done 或 plan-done 流程，不改变用户确认的人控边界。
  - 不要求删除所有代码示例、文件名或技术术语。少量示例在解释问题、约束或验收方式时可以保留。
  - 不判断实现方案是否正确，不替代 ADR 对齐、openspec validate、任务追溯或计划质量检查。
  - 不扩大到已生成的 design.md、spec.md、tasks.md 或执行计划的 HOW 内容审查。

## 关键场景
- GIVEN improvement 的 WHY/WHAT 段落包含多个代码围栏、函数签名和逐步实施指令，WHEN 内容审查运行，THEN 输出 warning，列出触发的信号和段落位置，但继续后续流程。
- GIVEN improvement 只包含少量代码术语或一个短示例用于说明约束，WHEN 内容审查运行，THEN 不因单一低强度信号单独触发 warning。
- GIVEN proposal 的范围描述包含具体文件清单，但没有函数签名、代码围栏或连续实施步骤，WHEN 内容审查运行，THEN 按低置信度处理，不默认阻断，并允许用户确认该细节属于必要范围说明。
- GIVEN warning 由过高的实施步骤密度触发，WHEN 用户查看报告，THEN 报告说明这是边界提示而非语义结论，用户可以保留原文、修改原文或忽略提示。
- GIVEN 内容包含一个合法的技术约束和对应验收标准，WHEN 启发式扫描运行，THEN 技术约束和验收表达不会仅因出现技术名词而被判定为 HOW 泄漏。
- GIVEN 检查器遇到缺失段落、非标准 Markdown 或无法解析的内容，WHEN 内容审查运行，THEN 检查以非致命方式结束，保留现有审查行为，并说明检查不可用或结果不确定。

## 技术约束
- MUST 采用保守、可解释的启发式信号，并分别记录代码围栏、函数签名、实现步骤密度和具体改动清单等命中原因。
- MUST 默认只输出 warning，不改变现有成功、失败和用户确认语义。
- MUST 支持按段落定位提示，并让用户看到触发信号，而不是只显示无上下文的分数。
- MUST 对单一弱信号设置足够的抑制条件，避免把正常技术术语、验收示例或范围边界误报为 HOW 泄漏。
- MUST NOT 使用 LLM、向量模型或不可解释的语义分类器作出默认判断。
- MUST NOT 自动改写、裁剪或删除 improvement/proposal 内容。
- MUST NOT 将 warning 升级为默认 hard block；如未来需要严格模式，必须沿用现有独立环境变量和 warning-to-error 约定，并另行评估误报数据。
- SHOULD 记录命中统计和人工确认结果，用于依据 ADR-0019 的实际数据决定阈值调整，而不是预先扩张规则集合。
- SHOULD 复用 ADR-0025 的分层审查入口，使 improvement 层与 proposal 层的提示保持一致，同时不重复已有的结构、ADR 引用和验收标准检查。

## 验收标准
- [ ] 对包含至少 2 个代码围栏、至少 2 个函数或方法签名，或至少 3 条连续实施步骤的样例，审查输出 warning，并列出具体命中信号和段落位置。
- [ ] 对只包含一个代码围栏、一个函数签名或少量技术术语的样例，审查不单独输出 HOW 泄漏 warning。
- [ ] 对包含必要范围文件名但没有其他高强度信号的样例，审查结果为通过或低置信度提示，不阻断流程。
- [ ] warning 输出明确标注“非阻断”和“需人工判断”，且创建、审批与 design-done 流程在默认配置下继续执行。
- [ ] 用户可在不修改检查器状态的情况下确认或忽略单次 warning，原始 improvement/proposal 内容保持不变。
- [ ] 缺失段落、空文件和非标准 Markdown 输入不会引发未处理异常，也不会改变现有内容审查结果。
- [ ] 单元测试覆盖每类启发式信号、弱信号抑制、段落定位、误报处理和非致命解析失败，覆盖率至少达到新增检查逻辑的 90%。
- [ ] 在现有 improvement/proposal 样本集上运行审查时，新增 warning 的人工确认误报率不超过 20%，并输出可复核的命中统计。
- [ ] 默认配置下现有测试套件通过，且未新增 LLM、向量数据库或外部运行时依赖。
