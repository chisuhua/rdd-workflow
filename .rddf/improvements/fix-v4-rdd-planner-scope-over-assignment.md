## 架构依据

v4 架构合并（D2b, 2026-09-04）将 `guide-design` / `guide-plan` / `guide-ship` 并入 `rdd-builder` 内部 6-phase 状态机后，`rdd-planner` 的职责边界出现系统性失配。Oracle 架构审查（2026-09-09）揭示三个互锁问题：

### 事实 1: §3.2 row 165 的 "planner author proposal.md" 是纸面设计，代码零实现

`docs/superpowers/specs/2026-09-04-rdd-workflow-v4-architecture-stage-merge.md` 第 165 行明确说 rdd-planner owns `openspec/changes/<name>/proposal.md (authoring only, no checkbox)`，Writes 列含 `proposal.md content`，HIL 标 "Medium (Phase 1 approval = 'approve proposal creation')"。

但实际实现：
- `_lib/cli/planner_cmd.py` 没有任何 authoring 子命令（仅 status/sync/attach/diff/advance-sprint/history/audit/feedback）
- `skills/rdd-planner/scripts/planner_stage_entry.sh` + `planner_stage_exit.sh` 都要求 `openspec/changes/<name>` **已存在**（否则 exit 2）——handoff 脚本以"change 由别人创建"为前提
- §9 demo 的 `rddf planner new/brainstorm/accept` 命令在真实 CLI 中**不存在**（对照 §5.1 CLI 清单同样缺）
- `proposals_authored` 字段是 grep 假值（`rddf roadmap list | grep -oE 'add-[a-z0-9-]+'`），不是 authoring 产物

**结论**：spec 文本声称的 authoring 责任从未落地为代码。

### 事实 2: ADR-0025 的 proposal.md 生成管线随 guide-design 删除后从未移植

ADR-0025 D1/D2 定义了 5-段 improvement → 完整 proposal.md 的转换契约（`generate_full_proposal.py`）。Wave 3（ADR-0044，commit `1095cec`）硬删除 `skills/guide-design/` 时：
- `generate_full_proposal.py` 一起消失，`grep -r generate_full_proposal` 全库零命中
- `skills/rdd-arch/scripts/approve_proposal.sh` 变成指向已删除路径的**坏 shim**（`exec .../guide-design/scripts/approve_proposal.sh`）
- `skills/rdd-builder/scripts/phase0_approval.sh` 的 D3 spec-delta 是**占位 stub**（写入 "Auto-generated by rdd-builder Phase 0 approve (per ADR-0025 D3)" 的假 Requirement，非 D1/D2 转换）

**结论**：当前 v4 中 **没有人**真正 author proposal.md 内容——实际产物是 `openspec new change` 脚手架骨架。

### 事实 3: §9 demo 与 §3.2/§3.4 内部矛盾

§9 demo（行 908-919）写 `rddf planner accept demo-change` → "✓ tasks.md scaffolded (no checkboxes yet)"，但：
- §3.2 row 166：builder owns `tasks.md`
- §3.4 Phase 1（行 224）：builder writes tasks.md（"NEW builder responsibility per user D"）
- planner SKILL.md not_owns L47：`openspec/changes/<name>/{design,tasks}.md`

同一份 spec 既 not_owns tasks.md 又被 demo 出"scaffold tasks.md"——不可调和的内部矛盾。

### 事实 4: ADR-0038 与 v4 promotion 直接冲突

ADR-0038 §Decision 1 写 "Implement `rdd-planner` as a **horizontal orchestrator** (NOT a sixth phase)"。但 v4 stage-merge spec §3.3 把 rdd-planner **promote** 为 full stage（per ADR-0042/0043）。spec frontmatter 自称 "Extends (additive, no conflict)" 是虚假声明——两者直接冲突。

### 影响

- **新加入者误读架构**：新人读 spec §3.2 会以为 rdd-planner author proposal.md，于是造"planner approve"幻觉（之前我犯的错就是这条路）
- **三方文档三个说法**：
  - `docs/superpowers/specs/2026-09-04-rdd-workflow-v4-architecture-stage-merge.md` §3.2：planner author
  - `README.md`：propose / add-improve 是"被 rdd-builder 调用"的子技能
  - `skills/propose/SKILL.md` L23：自述"被 guide-plan 调用"（stale，guide-plan 已删）
- **Builder P1 找不到 proposal.md 时的脆弱路径**：若新 change 不经过完整 pipeline，proposal.md 是骨架；verifier 验证时拿不到完整 Acceptance 内容

## 范围

**In Scope**：

### Part A — 文档补丁（~2-4h，Quick/Short）

A1. **spec §3.2 row 165**：移除 `openspec/changes/<name>/proposal.md (authoring only, no checkbox)`；"Writes" 列移除 `proposal.md content`；HIL 改为 "Medium (proposal lifecycle review / sprint governance)"
A2. **spec §3.2 row 166**：builder owns 增加 `openspec/changes/<name>/proposal.md (authoring via P0 approve, per ADR-0025)`
A3. **spec §3.3 schema v1**（行 188-202）：`.planner-handoff.json` 字段 `proposals_authored` → `proposals_ready`，并在 schema description 注明"attached for builder, 非 authoring 产物"
A4. **spec §3.4 Phase 0 input**（行 213）：`proposal.md (from rdd-planner)` → `proposal.md (authored at P0 approve per ADR-0025 D1/D2; 或 propose 子技能骨架)`
A5. **spec §9 demo**（行 908-919）：重写为 `rddf planner attach` → `rddf builder phase0 approve`（approve → proposal.md 生成 + spec-delta）→ P1 写 tasks.md；删除 `rddf planner accept` scaffold tasks.md 的段落
A6. **`skills/rdd-planner/SKILL.md` 行 14 + 41**：从 owns 删 proposal.md authoring；description 同步精简；not_owns（L45-50）增 `openspec/changes/<name>/proposal.md`
A7. **`skills/rdd-builder/SKILL.md` 行 28**：从 not_owns 删 proposal.md；owns（L20-25）增 `openspec/changes/<name>/proposal.md (authoring via P0 approve)`
A8. **`docs/adr/ADR-0025-design-proposal-creation.md`**：加 evolution note（v4 per ADR-0043：design 阶段并入 rdd-builder P0；本 ADR 的创建+审查前移决策继续有效，执行者改为 rdd-builder P0 approve 管线）
A9. **`docs/adr/ADR-0038-rdd-planner-crosscutting.md`**：amend "NOT a sixth phase" 条款（被 ADR-0043 双重身份取代：顺序阶段 + 横切编排器）；spec frontmatter "Extends (additive, no conflict)" 声明同步修正

### Part B — 实现补丁（1-2d，Medium）

B1. **移植 `generate_full_proposal.py`**：从 git 历史 `1095cec^` 或 `6587b98` era 恢复 → 进 `skills/rdd-builder/scripts/` → 挂接 `phase0_approval.sh` 的 approve 分支 → 替换现 D3 占位 stub
B2. **修复/删除 `skills/rdd-arch/scripts/approve_proposal.sh`**（当前指向已删除路径的坏 shim）
B3. **`skills/rdd-planner/scripts/planner_stage_entry.sh` + `planner_stage_exit.sh`**：`proposals_authored` 改为从 planner state / 已 attach 的 improvement 派生（删 grep 假值，与 schema 改名 `proposals_ready` 对齐）
B4. **（可选）planner-state schema v1.1** 增 `recommended_route` advisory 字段（**不动** planner-handoff schema）；planner `status` 输出展示 advisory 信号

### Out of Scope

- **复杂度 triage 归 planner 作为权威**：Oracle 明确否决。rdd-quick 自 triage（ADR-0047 D1）是正确位置——planner 信号集（improvement 5段+priority+phase）是 rdd-quick 信号集（plan+TDD+AC+代码近旁）的劣化子集；priority ≠ complexity；双 gatekeeper 冲突。可做 advisory 信号（recommended_route），不做路由权威。
- **`guides-design` 的 proposal 内容审查 4-层分离**：ADR-0025 D4 在 v4 中如何具体拆分（builder P0 审查 vs rdd-verifier 复审）待 future 评估，本提案不强制拆分。
- **ADR-0043 stage-merge 整体回退**：只修补 rdd-planner 职责失配，不动 stage-merge 主架构。
- **rdd-quick 与 rdd-builder 的统一入口**：当前 `skill_use("rdd-quick")` 自入口 + rdd-quick 自 triage 是正确设计，不整合。

## Impact

### 正向

- **架构清晰化**：rdd-planner 不再背负无法落地的"authoring"责任；rdd-builder P0 接管 proposal.md authoring（与 D3 spec-delta + 4-option approval 共位，符合 ADR-0025 D1 "生成→确认→落盘"）
- **新加入者不再踩坑**：spec §3.2 + SKILL.md 与代码一致，README/spec/SKILL.md 三方文档对齐
- **proposal.md 真正有内容**：移植 `generate_full_proposal.py` 后，新 change 的 proposal.md 不再是骨架，verifier 能拿到完整 Acceptance
- **Tasks.md 单一写入方**：消除 planner "scaffold tasks.md" 与 builder P1 "write tasks.md" 的内部矛盾

### 风险

- **破坏性变更可能**：A6-A7 的 SKILL.md 修改会改变 rdd-planner 的"authoring" 角色定位；下游若有 agent / 工具硬编码依赖此角色会失效（搜索 grep `planner.*authoring` 预检）
- **Wave 3 风险传染**：B1 移植 `generate_full_proposal.py` 可能引入 guide-design 时代的依赖（如过时 import）；需先静态 lint 再跑测试
- **rdd-arch/scripts/approve_proposal.sh 坏 shim**：若有测试在调用会挂；优先删而非修（避免传染）

### 兼容性

- **保留 4-option approval gate**（spec §3.4）：builder P0 不变
- **保留 .planner-handoff.json 字段名 + schema v1.1**（仅 `proposals_authored` 改名为 `proposals_ready`）；读方需同步改 schema consumer
- **保留 ADR-0047 rdd-quick 独立 skill**（rdd-quick P1 自 triage 不变）
